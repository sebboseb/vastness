# Generated-space reliability study

Question: how often does the unchanged intention → SDXL-Turbo → TRELLIS stack produce genuinely traversable generated free space? No gameplay, new interaction UX, style tuning, manual geometry repairs, or outcome-driven regenerations.

Predeclared plan: scripts/reliability/plan.json, 36 new jobs: nine categories × two distinct prompts × seeds7/42. Categories: tunnel, chamber, corridor, courtyard, doorway, bridge-like passage, cave, narrow passage, large open interior. Order is deterministic shuffled category blocks. No previous examples count toward the denominator. Every planned job counts, including inference/OOM/export/import/assessment/browser failures; infrastructure interruptions resume the same job ID, never a new seed. Keep all artifacts, failures, exact raw intent/derived constraints, worker/model commits, hashes, token counts and timings. Mac API gains optional validated development seed, default42 unchanged; no input UX changes.

Primary endpoint: scale6, original generated support, radius.3m/body1.8m, maxStep.25m/maxSlope35°, at least3m reversible route and1m sustained enclosure, safe exterior scaffold seam, successful coarse-rendered browser entry/traversal/return. Use the already-tested assessor unchanged, including its bounded search and nine-probe limitation. Scales10/12 are prespecified secondary sensitivity results, not replacements for primary failure. Open bridge/courtyard requests retain the same enclosure criterion (opposing walls/parapets can satisfy it); also report supported free-space existence separately to expose criterion/category mismatch.

Run each candidate once. Source-image fidelity, mesh topology, conservative voxel mismatch, pipeline resource bounds and browser failure are separate axes. Record generation latency, whole-device sampled peak VRAM, PLY/GLB bytes/triangles, generated floor/support evidence, enclosure, reversible route, length/displacement, step/clearance/entry rejection metrics and practical cause. Do not label all unsupported footprints as literally no floor, or bounded-search failure as mathematical impossibility. Annotate visual reasons after measurement; preserve uncertain diagnoses. Report overall and category pass counts, prompt-paired seed consistency, Wilson95% interval (descriptive convenience sample, not population guarantee), primary vs scale-adjusted results, and machine-readable rows.

## Diagnostic replay amendment (after the first nine jobs)

The unchanged baseline remains the primary study. On 2026-09-16, actual browser trials revealed a movement-step-dependent entry rejection: floor sampling admitted a boundary a few nanometres beyond a triangle, while continuous-support clipping used a different tolerance. Larger offline steps passed; smaller browser steps stopped. This is a validator/runtime defect, not evidence of a missing generated floor.

After all 36 baseline candidates and eligible browser trials finish, freeze their evidence. In a separate prototype worktree, make only the numerical tolerance correction, with step-size-invariance regressions and true-gap negative controls. Do not edit original geometry, prompts, seeds, models, scales, enclosure requirements or the accepted M0/M1 source tree. No new GPU jobs belong to this replay.

Reassess the same 36 hash-identical artifacts at all three declared scales using the corrected navigator, then test every newly eligible browser route through the same coarse renderer and controls. Store all replay assessments, visits and browser evidence separately under `.runtime/reliability-replay`. Report the paired baseline/replay results explicitly; the replay is a diagnostic follow-up prompted by the observed defect, not a pre-generation preregistered result. Do not overwrite failures or present the corrected rate as the unchanged pipeline's rate. Keep enclosure-only rejection separate from evidence of absent navigable open space.
